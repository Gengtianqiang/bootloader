# 第 13 课：安装中断、首次启动与回退

前置：第 11、12 课。状态决策示例已提供，安装/恢复执行器待实现。

## 状态执行约定

| 持久状态 | 必须具备的事实 | 复位后处理 |
|---|---|---|
| NORMAL | 当前 App 已确认 | 校验后运行，或恢复接收 |
| DOWNLOADING | 旧 App 尚未覆盖 | 放弃不完整候选，运行旧 App/恢复接收 |
| DOWNLOADED | 完整候选和元数据已提交 | 准备并验证 staging、backup |
| INSTALLING | staging 和 backup 已可靠保存 | 从持久候选重新完成安装，不能运行半份 App |
| TRIAL_READY | 新 App 安装后校验通过 | 提交 TRIAL_RUNNING，开启 IWDG 后交接 |
| TRIAL_RUNNING | 新 App 尚未提交健康确认 | 检查复位原因，按明确策略恢复旧版 |
| ROLLING_BACK | 备份已验证 | 继续恢复并校验旧 App |

Ota_SelectAction 只输出动作；执行器还要判断对应镜像和记录是否有效。若候选/备份都不可用，进入接收恢复，不无限重复破坏性动作。

## 安装提交点

保持 download/staging/backup 独立。先完成旧版备份并校验，再提交 INSTALLING，之后才擦内部 App。写完新 App 后读回校验，再提交 TRIAL_READY。整个流程允许重启重做且不覆盖唯一恢复来源。

## IWDG 实验

开狗后不能靠普通函数任意关闭。新 App 必须了解继承的看门狗状态，并在约定时间内完成健康确认。超时时间按 LSI 频率容差和实际启动耗时选择，不把示例计数当精确秒表。

健康确认不宜放在进入 main 的第一行。至少关键时钟、存储和业务初始化通过，若有 RTOS，还要确认必要任务正常。确认协议可以选择持续喂狗或按约定再次复位；要解释为何不会造成复位循环。

## 故障注入

1. 在新 App 确认前死循环，验证 IWDG 复位和旧版恢复。
2. 安装中途断电，验证从 INSTALLING 恢复，不运行残缺 App。
3. 回退中途断电，验证 backup 没被覆盖，仍可继续。
4. 候选或备份 CRC 错误，进入明确接收恢复。

不要用 JumpToApp 后面的代码作为唯一回退路径；App 一旦跑飞通常不会返回。

## noinit 进阶

原教案 g_JumpInit 固定地址用于跨软件复位的快速交接。若研究此机制，在 GNU ld 中显式预留 .noinit (NOLOAD)，避开栈和 data/bss 清零，并核对复位类型。它不能代替掉电持久化。

验收：用记录和复位原因证明状态变化，而不是看到灯亮就推断版本正确。
