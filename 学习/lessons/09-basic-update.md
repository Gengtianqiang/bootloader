# 第 09 课：第一次串口升级闭环

前置：第 04～08 课验收通过；参考 09 原教案主调用链。

## 本课里程碑

```text
Boot 进入接收模式
  → 接收 OTA1 包头
  → 检查地址和长度
  → 接收有效载荷并写内部 App
  → 校验读回 CRC/向量
  → 复位或交接，运行新 App
```

此阶段直接修改 App 区，下载中断可能使 App 失效。目标是最小可解释闭环；第 10～13 课再加入不破坏旧 App 的暂存和恢复。

## 先设计入口

main 不再无条件优先跳 App。使用按键、串口命令或明确的调试开关进入下载模式；输入不存在且 App 有效时才正常启动。按键引脚需要确认后接入。

新增 boot_manager 目标/模块，main 只负责组装：读取启动条件、选择动作、执行；UART、Ymodem、镜像解析、Flash 后端分别保持边界。

## 实验步骤

1. App 版本设为 1，保存 ELF/BIN 与观察记录。
2. 修改 App 版本和心跳周期为版本 2，构建并打包。
3. 上位机通过 Ymodem 发送 .ota，协议接收端先剥离包头，只有载荷写入 App 基址。
4. 收完必须检查精确长度、CRC 和向量；失败留在 Boot 接收模式，不尝试执行残缺镜像。
5. 断开调试器，复位验证新版本。

## 故障与验收

错误 load address 在擦除前拒绝；CRC 错误不启动 App；中途停止传输后 Boot 仍能进入下载恢复。不能用调试器重新下载 App 后宣称串口升级成功。

检查预设和 map：Boot 仍限制在 32 KiB。体积超出时分析库/日志/协议占用，必要时明确调整分区并重建两个镜像；不删除链接边界。

解释这个版本为什么还不具备可靠回退：旧 App 已被逐步覆盖，仅保存一份长度或状态标志无法还原代码。
