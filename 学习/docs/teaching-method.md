# 后续逐课教学约定

这份文件用于让后续会话沿同一条路线推进。先读 progress.md 和上一课实验记录，不因为“代码已提供”就认定学习或硬件验收已完成。

## 一次会话的节奏

1. 明确本课一个结果，连接上一次已经观察到的事实。
2. 用当前工程的一小段源码解释原理，不先引入本课用不到的完整抽象。
3. 让学习者预测一次改动会发生什么。
4. 学习者执行命令或硬件操作，保存最小必要证据。
5. 根据证据诊断；把编译错误、链接错误、运行错误分清。
6. 回答课末问题，更新记录与进度，再进入下一课。

助手可以准备、解释、审查和修改实验代码；沿用当前用户偏好，不主动执行固件构建、下载或设备操作。手册里的构建命令是供学习者自行执行的步骤。PC 端数据格式测试与板上固件验收分开报告。

## 当前从哪里开始

先从第 01 课开始，直接使用用户自己的 otatest 和 bootloader。先读 docs/project-comparison.md，再对比两份 Preset、工具链、根 CMakeLists 和子目录。不要先要求用户学会新生成的 Firmware.cmake 或切换到实验 main。

第一轮只要求回答：

- 两份 Debug 的源码目录与 binaryDir 分别是什么？
- 两份 main.c 分别从哪个 CMakeLists 加入目标？
- toolchainFile 何时生效，编译命令与链接命令有何区别？

不要一开始要求用户掌握全部 14 课。问题没有答对时，回到具体文件和实际输出再解释。

## 代码与解释的尺度

01～04 以原工程为主线，模块化示例只作对照；原 otatest 当前不是偏移 App，第四课才指导修改 ld 和 STM32_Drivers 的向量宏。原 Boot 已有跳转，先解释它再重构。05 起每次实现一个最小组件，再连接到用户的两个工程；参考学习目录的库边界时明确差异。

开课时先确认终端和 CMake Tools 当前选择的是原 otatest、原 bootloader 还是学习目录中的实验工程。三个目录都有 Debug 名称，不能混用构建目录和 ELF。最终安装器、元数据和回退不能只用 TODO 标注后声称完成。

讨论协议与存储时总要说清：当前缓冲区归谁、有效长度是多少、数据何时可靠落盘、失败后还剩哪份可恢复镜像。讨论 CMake 时总要说清：参数属于哪个目标、是否传播、是否导致重新配置/编译/链接。

所有“通过”必须限定证据范围。路径存在不是工具链可构建；编译成功不是中断正确；向量合法不是整镜像完整；灯亮不是已完成首次启动健康确认。
